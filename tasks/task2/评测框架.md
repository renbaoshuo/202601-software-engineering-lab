# QueryPilot Agent 评测框架

## 1. 评测目标

QueryPilot 面向数据库课程学生和初级开发者，帮助用户理解 SQL 报错、发现查询结果与目标之间的偏差，并在修改后再次核对结果。因此，评测既要关注回答是否正确，也要关注它能否帮助用户理解问题、完成修改，以及结论是否值得信任。

我们希望了解：加入固定工具反馈后，诊断有没有改善；允许通用 Agent 自主、多轮调用工具后，是否带来更多帮助；在此基础上加入 QueryPilot 的领域指令和知识库，又会产生什么变化。等待时间和模型用量也分别记录。

同一道测试题还将分别放在新会话、固定前序提问和随机前序提问之后，观察四组回答是否受到上下文影响，以及相同条件下重复作答是否出现明显波动。

## 2. 评测对象

| 对象 | 评测条件 | 主要比较目的 |
| --- | --- | --- |
| A：单模型 | 提供题目、SQL 和必要背景，每次用户提问后单次作答；不提供工具反馈或工具调用权限 | 了解基础模型直接回答的表现 |
| B：模型＋固定工具反馈 | 在相同原始信息上补充真实的 SQL 静态检查和执行反馈，每次用户提问后单次作答；不开放自主工具调用 | 与 A 对比，观察固定工具反馈带来的变化 |
| C：通用 Agent | 提供相同原始任务，开放 SQL 工具，允许自主选择和多轮调用；不加入 QueryPilot 的领域指令和知识库 | 与 B 对比，观察自主选用工具和多轮调用带来的整体变化 |
| D：完整领域 Agent（QueryPilot） | 在 C 的基础上加入 QueryPilot 的领域指令和知识库，其余 SQL 工具、数据和运行限制一致 | 与 C 对比，观察领域指令与知识库共同带来的变化 |

四组做同一份评测，使用同一基础模型和相同的原始任务信息，按照下述共同标准比较。两种 Agent 共用 SQL 工具接口、数据和资源限制，均保留工具说明及 SQLite、单条只读查询等基本约束。

B 与 C 的差别包括是否自主选择工具、是否进行多轮调用，以及能否按需获取新的反馈；D 比 C 同时增加领域指令和知识库。比较时分别说明这些整体变化，具体运行设置由方法部分补充。

## 3. 评测内容与依据

下表的章节号对应项目《软件需求规格说明书》，方便核对每个评价点的来源。

| 项目目的与依据 | 要评什么 |
| --- | --- |
| 诊断报错和查询结果偏差（2.3、3.2.2.3.3） | **有没有找准问题。** 能否区分语法错误、运行错误和可能的逻辑问题，说明真正影响结果的原因。 |
| 帮用户修改并再次验证（1.2、3.2.2.3.4） | **修改建议是否有效。** 建议是否能执行，是否有助于完成原题，而不是只消除报错。 |
| 面向课程学生和初级开发者（1.2、2.3） | **解释是否正确、容易理解。** 能否讲清为什么出现问题、为什么这样改，以及还需要核对什么。 |
| 用实际工具结果和领域知识支持诊断（3.2.2.3.3、3.2.3） | **结论是否有真实、相关的依据。** 提到执行结果或知识资料时，它们是否真实存在、能够支持当前结论；未验证的建议是否说明。 |
| 认可正确查询，信息不足时先说明并询问（3.2.2.3.1） | **能否作出恰当判断。** 已符合已知目标的查询不强行挑错；信息不足时说明已知部分，并询问影响判断的内容。 |
| 使用内置数据集上的 SQLite 只读查询（2.4、3.4.3） | **建议是否符合实际使用范围。** 能否使用真实存在的表和字段，遵守 SQLite 规则及只读限制。 |


### 3.1 先检查达标底线

正确性、真实性和项目限制是所有回答都必须满足的要求，通过这些要求本身不加质量分。

| 底线 | 通过要求 |
| --- | --- |
| 关键内容正确 | 关键诊断、SQL 规则和修改方案没有实质错误，完成当前输入要求的核心任务。需要修复时，方案能执行且结果符合已知目标；不能只消除报错却漏掉目标条件。 |
| 判断方式正确 | 正确查询应被认可，不把合理写法当成错误；信息不足时指出影响结论的缺失内容，并询问必要信息，不编造唯一答案。 |
| 依据真实 | 不虚构执行、输出、表结构或知识来源；候选建议不能说成已经运行验证。 |
| 符合运行范围 | 建议执行的查询和操作符合内置数据集、SQLite、单条只读查询的限制。 |

任一底线未通过，该题正式得分为 0 分，并记录失败原因。

通过底线后，再按下表判断回答提供了多少诊断和学习帮助。对于只给出正确结论、没有展开说明的回答，可以通过正确性底线，但不会获得各质量项的分数。

### 3.2 质量得分点与分档

质量分为诊断、解释、建议、证据四个方面，每个方面包含两个得分点。每点取 0、1、2 分，满分 16 分。下表的 0 分表示没有展示该项帮助。

| 得分点 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| **1. 指出哪段 SQL 造成了什么问题**（诊断） | 只说“连接有问题”，没指出是哪条连接条件、哪个列名或哪个筛选条件。 | 指出具体 SQL 部分，或说出“少了哪些学生”等结果问题，但没说明两者的关系。 | 把具体写法和结果问题连起来。例如指出 WHERE 中的成绩筛选，会漏掉没有符合条件选课记录的学生。 |
| **2. 说清什么情况下会出问题**（诊断） | 只说“可能有很多原因”，没说明与本题哪种数据或表结构有关。 | 提到本题相关条件，如空值、重复记录或没有匹配记录，但没解释这些条件为什么会影响答案。 | 说明这个条件怎样引发问题，以及条件改变后结论是否仍成立。例如所有学生都有符合条件的选课记录时，当前数据里可能看不出漏人的问题。 |
| **3. 按步骤解释 SQL 怎样得到这个结果**（解释） | 只贴改好的 SQL，或只说“NULL 要特别处理”，没有解释本题。 | 讲了本题会用到的规则或某一步，例如 WHERE 会筛选记录，但没说明哪些记录会被筛掉。 | 结合本题把相关步骤连起来。例如先连接得到哪些记录，再筛掉哪些记录，最后为什么漏人或算错人数；所用概念结合本题说明。 |
| **4. 用小例子把查询结果讲明白**（解释） | 只有抽象解释，没有用数据例子、手工计算或 SQL 片段说明本题。 | 举了与本题有关的一行数据，或列出一段 SQL，但没说具体会查出哪些记录、数值，或出现什么错误提示。 | 用例子说出具体的预期记录、数值或报错；需要修改时，还说明改前改后的差别。例如改前某学生不出现，改后应该仍保留，选课信息为空。 |
| **5. 说明改哪里，以及为什么这样改**（建议） | 只贴一整段新 SQL，没有说明改了什么、各处改动解决什么要求。 | 指出改动，例如“把成绩条件移到 ON 中”，但没有说明为什么这样能保留题目要求。 | 说明各处关键改动的作用，以及怎样保留原题要求。例如把成绩条件放进连接条件，让没有符合条件选课记录的学生仍然保留。 |
| **6. 告诉用户怎样检查是否改好**（建议） | 只说“改完再运行看看”“自行检查”，没说检查什么。 | 让用户检查本题相关的记录或数值，但没说明正确时应该是什么样，或怎样判断是否通过。 | 同时交代检查对象、应该出现的结果和成功条件。例如核对没有符合条件选课记录的学生是否全部保留，选课信息是否为空。 |
| **7. 让关键说法有能核对的根据**（证据） | 只有结论，没指出题目、SQL、数据或规则中的哪些内容支持它。 | 给了相关的表结构、数据、规则或真实工具结果，但只有部分关键说法有根据，或没说明这些材料支持哪条说法。 | 每个关键说法都能找到对应根据。例如指出题目要求保留所有学生，而 SQL 中的某条件会过滤掉哪些学生，因此不符合要求。 |
| **8. 说清这次检查能确定什么**（证据） | 只说“可能”“未运行，仅供参考”，没有说明具体哪件事已经确定或尚未确定。 | 说出具体已知或未知内容，例如还不知道“按班级还是全校统计”，但没说它会影响什么判断。 | 说明已有材料能确定哪些结论；如果还有关键未知，说清它会改变哪个判断、需要补什么。例如统计范围未明确时，不能直接认定必须按班级分组。信息充分时，无需另编限制。 |


### 3.3 SQL 有错、没错或信息不足时怎样评分

有的 SQL 本来就是正确的，有的还缺少判断条件，因此每份回答需要做的事不同。本节说明这三种情况分别看什么，避免要求所有回答都重新写一段 SQL。

| 题目情况 | 评分时看什么 |
| --- | --- |
| SQL 确实有错 | 先检查是否找对错误、改法是否正确。再看能否指出哪段 SQL 造成了什么问题，解释为什么这样改，并告诉用户怎样确认结果已经符合题目。 |
| SQL 本来就正确 | 正确做法是认可原查询。诊断和解释项看是否说出原 SQL 的哪些写法满足了题目要求、为什么不需要改；建议项看是否说明应保留的写法及其作用，并给出核对结果的办法。 |
| 缺少判断所需的信息 | 例如“统计人数”没说按班级还是按全校统计，应先问清这一点。评分看是否指出具体缺少哪个条件，解释不同答案会让分组方式或输出结果有什么不同，提出可以回答的具体问题，并说明补齐后怎样继续检查。 |

三个场景都可以用题目、SQL、表结构和规则推导支持回答；用过执行或检索工具的，也可以提供真实记录。是否使用工具本身不加减分。

### 3.4 测试集设计（测试题按哪些要求编写）

题目需要给出足够信息，让模型有机会展示上述能力。出题时需同时准备：①给被测模型/Agent 看的**任务 Prompt**；②评分人查看的**标准答案（Ground Truth）**与参考执行结果。

#### 3.4.1 测试集规模与划分
- **规模**：共准备约 **30 个**案例。
- **集合划分**：划分为**开发集**与**最终留出集**。提示词调优和知识库调整仅使用开发集；在正式测试前固定留出集案例、预期答案与评分规则。凡用于演示或调优的案例均归入开发集，最终留出集结果用于报告领域定制效果。

#### 3.4.2 案例覆盖类别（8 类）
测试集需覆盖以下题型，以确保能够全面检验各组表现：
1. **语法与列名错误**（拼写错、表名错、缺逗号等）
2. **WHERE 与 NULL 逻辑**（如 `!= NULL`、遗漏 `IS NULL` 的判断）
3. **JOIN 错误**（如 INNER JOIN / LEFT JOIN 混用导致漏数据、笛卡尔积）
4. **聚合与分组错误**（GROUP BY / HAVING 使用不当）
5. **子查询与 CTE**（嵌套逻辑错误、相关子查询误用）
6. **排序与 LIMIT 错误**（排序依据错误、截断过早）
7. **正常查询**（原 SQL 正确，考察是否会强行挑错）
8. **信息不足**（如未说明按班级还是全校统计，考察是否主动询问）

#### 3.4.3 单条案例的字段定义
每个案例在数据表/JSON 中需包含以下字段：
- `task_id`：唯一标识
- `category`：所属题型（上述 1–8 类）
- `split`：属于开发集（dev）还是留出集（test）
- `schema`：涉及的表结构
- `sql`：待诊断的原始 SQL
- `goal`：自然语言的查询目标
- `ground_truth`：人工确认的正确结论（若有错，说明真正的错误点）
- `acceptable_explanation`：可接受的解释范围
- `expected_tools`：供评分核对的参考工具证据（如解析结果或执行记录），不要求被测方案复现固定调用路径
- `knowledge_id`：关联的知识库条目 ID（如有）

#### 3.4.4 出题标准

| 题目和标准答案需要准备什么 | 希望看出什么差别 |
| --- | --- |
| 题目给出查询目标、SQL 和必要表结构；标准答案说明真正的错误，或说明原 SQL 为什么正确。 | 只猜“JOIN 可能错了”，还是能说出哪条连接或筛选条件让哪些记录漏掉。 |
| 能让问题出现的数据或条件，以及用来比较的情况，例如有、没有符合条件的选课记录。 | 只记住一种常见错法，还是知道什么数据或要求下会出问题，条件变了以后该怎样判断。 |
| 能核对的具体记录、计数、报错，或修改前后结果。 | 只背规则，还是能用规则解释本题哪些记录或数值发生了变化。 |
| 原题必须满足的要求，以及正确时应该看到什么。 | 只给正确答案，还是能说明改动的作用，并告诉用户怎样检查结果。 |
| 题目已经给出的信息、可用记录，以及故意没有说清的关键条件（如有）。 | 只说“答案是这样”，还是能说明凭什么这样判断、哪些结论还需要补信息。 |


### 3.5 得分示例

以下只示意两个得分点，不是正式测试集。假设目标是保留所有学生，同时只列出高于 60 分的选课记录，没有符合条件的记录时仍保留学生。原查询先用 LEFT JOIN 连接学生和选课记录，再用 WHERE 筛选成绩，导致部分学生消失。

假定完整回答已经给出正确判断和改法，下表只摘取其中一部分，说明同一个得分点怎样区分 0、1、2 分。

| 观察项目 | 回答中展示的内容 | 该点得分 |
| --- | --- | --- |
| 指出哪段 SQL 造成了什么问题 | “连接有问题。”没有指出哪段 SQL。 | 0 |
| 指出哪段 SQL 造成了什么问题 | “问题出在 WHERE 中对选课成绩的筛选。”指出了 SQL 部分，但没说会漏掉谁。 | 1 |
| 指出哪段 SQL 造成了什么问题 | 指出 WHERE 中的成绩筛选会排除没有选课记录、或所有成绩都不高于 60 分的学生，结果漏掉题目要求保留的人。 | 2 |
| 告诉用户怎样检查是否改好 | “改完再运行看看。” | 0 |
| 告诉用户怎样检查是否改好 | “检查没有符合条件选课记录的学生。”有检查方向，但没说正确时应该看到什么。 | 1 |
| 告诉用户怎样检查是否改好 | 核对这些学生是否仍全部出现、选课信息是否为空；若缺少任何一个学生，说明仍未满足保留要求。 | 2 |

### 3.6 测试方法与消融定位

1. **控制变量**：A/B/C/D 四组使用同一基础模型、相同采样参数、相同输入案例集和输出长度上限。B、C、D 使用同一执行数据；C、D 共用 SQL 工具接口、资源限制与 SQLite、只读查询等基本约束，D 额外启用领域指令和知识库。
2. **比较各项设计带来的变化**：
   - **A → B**：观察加入固定静态检查与实际执行反馈后，回答质量有什么变化；
   - **B → C**：观察自主选择工具、多轮调用和按需获取反馈带来的整体变化；
   - **C → D**：观察 QueryPilot 领域指令与知识库共同带来的变化。
   - 四组使用相同的正确性底线和 16 分质量标准，不因工具调用次数或组别直接加分。
3. **D 组内部消融（可选）**：需要进一步区分领域指令和知识库的作用时，可在部分开发案例上保留领域指令、关闭知识检索，与完整 D 组比较；这类补充分析单独记录，不替代四组主对照。
4. **评分流程**：至少两人独立评分，存在争议时交由团队复核；严格记录“引用缺失”与“引用错误”、“SQL 执行返回错误”与“工具基础设施故障”。保留超时、空回答、失败和重试记录。
5. **结果呈现**：报告需如实呈现改进、持平或退化的情况。展示典型案例的原始输出、工具证据及评分依据，所有准确率、延迟和费用仅填写实际测得的数据。

### 3.7 三类对话条件下的表现

围绕需求说明书 3.2.2.3.1 中的上下文处理，同一道测试题 Q 在下列三类对话中交给四组回答，比较上下文是否影响最终得分和任务完成情况。

| 对话条件 | 对话怎样安排 | 本次评价什么 |
| --- | --- | --- |
| 直接提问 | 新会话中只提出 Q，收到回答后结束 | 没有前序交流时，对 Q 的回答 |
| 固定前序提问 | 新会话中先按固定顺序交流预先确定的问题，再提出 Q | 固定对话历史之后，对 Q 的回答 |
| 随机前序提问 | 新会话中先交流随机抽取的固定数量问题，再提出 Q | 随机对话历史之后，对 Q 的回答 |

固定与随机条件采用相同的前序提问次数。随机问题在同一批比较前抽定，四组共用同一用户提问列表和顺序，各组保留自己的真实回复及工具记录。每类对话从新会话开始，段内保留历史；Q 的题目、SQL、数据、必要背景和评分要求相同，前序问题不改变其目标，也不提前提供参考答案或补齐信息不足题故意缺少的条件。各组在 Q 上的工具权限和运行限制保持一致；A、B 是每次用户提问后单次生成，C、D 可按需多轮调用工具。

只对 Q 的回答使用现有底线与 16 分标准，前序问题不累计加分；历史记录仅辅助核对 Q 引用的真实证据。分别比较每组在三类条件中的得分、底线通过和任务完成情况，再比较四组受到的影响。前序交流与 Q 的时间、用量分别保留。同条件可独立重复，记录每次结果；重走同一提问列表与重新随机抽题分开记录。前序次数、问题池和重复次数由后续方法确定。

该设计粗略比较本批对话条件下的表现，历史内容、长度和前序回复都可能产生影响，不将差异全部归因于上下文长度。若系统筛选或截断历史，需记录实际采用的上下文。用户明确改动任务要求时，答案相应变化不算不稳定。

## 4. 评测原则

最终重点看诊断、建议和解释的质量。调用了多少工具、回答写了多长，都不直接构成优势。正确且有分寸的回答应得到认可。

回答不能编造事实或把未验证的内容说成已验证。有真实执行记录、可核对的知识来源，可以体现证据更充分；没有引用与引用错误应分开看。

根据需求说明书 3.6.2，另将等待时间和模型用量作为辅助指标，与诊断质量分别展示：

| 辅助指标 | 比较内容 |
| --- | --- |
| 等待时间 | 从提交任务到完整回答结束的总耗时，包含生成固定反馈、工具执行和全部模型调用，反映用户需要等待多久。 |
| 模型用量 | 每道题所有模型调用累计的输入、输出 token 及总量，以模型服务返回的用量为准，反映完成诊断需要多少模型资源。 |
