# QueryPilot Alpha 冲刺计划

> 团队名称：组长说的都队

## 前期工作回顾与思考

在第一次作业中，我们通过需求调研明确了 QueryPilot 的定位：面向数据库课程学习者和 SQL 初学者，帮助大家看懂报错原因、理清查询结果与预期之间的偏差，并在修改后能够亲自验证结果。到了第二次作业，我们进一步完成了产品原型、系统设计和评测方案的规划，目前项目的基础框架也已经搭建完毕。

回头总结前两轮的工作，我们也发现了一些问题：之前的设计大多还停留在文档和原型图上，不少设想偏理想化，比如实际开发时前后端怎么顺畅衔接、SQL 运行与 Agent 诊断怎么真正串成一个闭环、知识库和评测在实际案例中效果如何，这些都还没有经过真实运行环境的检验。同时，Alpha 冲刺只有两周时间，如果一上来就想把所有功能一次性做全，很容易在局部细节上消耗过多精力。因此，本轮冲刺我们决定先收敛范围，集中力量打通最核心的查询与诊断流程，先把系统做成稳定可用的基础版本，再逐步完善辅助功能。

## 本轮目标与改进思路

本轮 Alpha 冲刺的主要目标，是让 QueryPilot 从原型和设计稿真正落地，交付一个核心流程完整、能够顺畅演示的可用版本。我们优先打通从选择数据集、编写并运行 SQL，到唤起 Agent 诊断、按建议修改并重新验证这一条主链路；至于会话搜索、历史导入导出、附件预览等拓展功能，则放到主流程稳定之后再视情况推进。

围绕前期发现的不足，本轮主要从以下几个方面进行改进：

| 前期反思与不足 | 本轮改进思路 | 预期效果 |
| :---- | :---- | :---- |
| 原型只定义了静态页面和理想状态，实际的前后端交互与反馈细节还需要对齐。 | 先统一前后端的基础数据约定，优先接通数据集浏览与 SQL 直接运行能力，再逐步接入模型配置和 Agent 诊断。 | 即使暂未配置大模型，也能正常浏览表结构并运行查询；各种正常或异常情况都有清晰的界面反馈。 |
| 光能运行 SQL 只能确认语句没有语法报错，用户更需要知道结果为什么不对，以及改完后是否真的有效。 | 把 SQL 运行环境与智能体诊断打通，让 Agent 能够结合真实的表结构、分析结果和执行反馈来定位问题，并支持用户改完后在当前会话里直接复验。 | 面对常见的 SQL 报错或结果偏差，Agent 能给出有依据的诊断说明和修改方向，分析过程和验证结果清晰可见。 |
| 调试 SQL 时往往需要反复修改，需要保证记录不错乱，同时兼顾个人配置的信息安全。 | 在本地维护草稿、对话和运行记录的对应关系；用户的模型配置信息仅在发起诊断时按需使用，不在服务端留存。 | 切换会话或刷新页面后，草稿和已完成的诊断结果都能正常恢复；个人密钥等敏感信息不会外泄。 |
| 前期规划了知识库和评测方案，但还需要落地具体内容并用实际案例检验效果。 | 整理并交叉核验一批常见 SQL 规则与错题知识接入检索，同时准备好覆盖不同问题类型的测试案例，开展多组对照评测。 | 诊断时能够检索并引用可靠的知识条目，减少凭空判断；通过对比评测明确领域设计带来的效果提升，并记录待改进的问题。 |

此外，当外部模型服务临时出现波动或暂不可用时，工作台本身的浏览和运行功能仍可独立使用，待连接恢复后再继续发起诊断，尽量保证基础练习体验不中断。

## 冲刺日程与协作安排

本轮 Alpha 冲刺计划持续 14 天，按阶段稳步推进：

| 时间 | 阶段任务 | 阶段目标 |
| :---- | :---- | :---- |
| 第 1–2 天 | 全组一起拆解本轮任务并落实分工，前后端先对齐基础的数据交互约定，知识库和评测组同步确定各自的整理标准与设计思路。 | 明确任务清单与分工，各小组顺利启动。 |
| 第 3–5 天 | 打通数据集浏览、表结构查看和 SQL 基础运行链路，搭建起工作台核心界面；知识组开始整理并核对首批知识条目。 | 实现工作台基础 SQL 编写与运行功能，完成初步联调并发布首个阶段版本。 |
| 第 6–9 天 | 接入个人模型配置、Agent 诊断与知识检索能力，把诊断过程展示、修改复验和本地记录保存串起来；评测组完成测试案例与评分标准的整理。 | 跑通从运行查询到 Agent 诊断、修改后再验证的完整主流程。 |
| 第 10–12 天 | 组织开展多组对照评测，检验整体诊断效果；同时对主流程和断线、报错、会话切换等常见异常情况进行集中测试与回归，优先修复影响核心体验的问题。 | 拿到初步评测对比结果，完成关键缺陷的排查与修复。 |
| 第 13–14 天 | 在演示环境再完整走一遍部署与验收流程，汇总每日进度与各成员的工作记录，准备好答辩 PPT 并完成冲刺 Vlog 剪辑。 | 主流程验收通过，按规范发布 Alpha 版本，完成本阶段交付准备。 |

在日常协作上，我们每天安排一次 10 分钟左右的站立会议，全员参加，如有特殊情况缺席会在当天日志中说明原因。站会上主要快速同步三件事：昨天做了什么、今天准备做什么、遇到了什么卡点；具体的技术或方案细节不在会上展开讨论，会后由相关同学直接对接解决。任务进度统一在 GitHub 仓库中更新跟踪，产品同学每天记录剩余工作量以便绘制燃尽图，也会注意留存平时交流和联调的真实片段，方便后期剪辑冲刺 Vlog。
